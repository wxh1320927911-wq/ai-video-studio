# 05 · 解禁模型与主机调整

> 背景：`04-规划机选型.md` 选的官方版 `qwen3.6:27b` 带安全对齐，写黑暗向、暴力、擦边类 H3 提示词时会拒答或自动净化。需要换成解禁（abliterated / heretic）版本。
> 结论：**主选 JonathanColetti/Qwen3.8-27B-Uncensored，Q4_K_M 量化（15.66GB，MTP 内联），主机沿用 RTX 3090，选内蒙B区（¥1.48/时）。** DavidAU 那版降为 A/B 对照组，0bserverx 版作为第二替补（主选仍拒答时才启用）。

> 核对日期：2026-09-20，价格与下载量以官网 / HF 页面为准。

## 二、模型选择：候选池扩到全站

### 2.1 怎么筛的

初版只在 DavidAU 一家里挑，理由是"他在 Qwen 解禁圈最有名"。这是**样本偏差**——等于只在一个人家里找最合适的东西。

这次改成全站筛：HF 模型库按 `text-generation` 过滤、关键词 `Qwen3.8-27B`、按下载量排序，取前 30 名，把名字里带 `Uncensored` / `Abliterated` / `Heretic` / `OBLITERATED` / `Unleashed` 的全拎出来比。

为什么把基座锁死在 **Qwen3.8-27B**，而不是"全站任意解禁模型"：

- **同一基座才能做 A/B。** 我们要量的是"解禁带来多少收益、格式损失多少"。换基座就变成两个变量同时动，测不出因果。
- **27B 是 24GB 卡上的甜点。** Q4_K_M 落在 16–19GB，装得下还有余量；再大一档（40B）Q4_K_M 就约 24GB，24GB 卡正好装不下。
- **Qwen 的结构化输出能力在同尺寸里最强**，而我们的任务本质就是"按模板填结构化字段"。

### 2.3 为什么主选从 DavidAU 换成 JonathanColetti

这是本轮调研最重要的结论变更。理由按重要性排序。

**1. 它是唯一"零微调"的候选，格式能力与基座等价。**

JC 的模型卡把方法写得很直白：

> Refusal directions removed with Heretic, which co-minimizes refusal count against KL divergence from the base model. **No handwritten refusal removal code, no finetuning, no additional training data.** … Capabilities, training data, and architecture are otherwise unchanged.

也就是说它**只做了一件事**：把拒绝方向从权重里减掉，而且在"拒答数"和"与基座的 KL 距离"之间做联合最小化。除此之外，权重就是原版 Qwen3.8-27B。

而本文档第八节自己写着：**解禁 ≠ 格式遵循更好，这是最需要警惕的一点。** DavidAU 那版是 `Qwen3.6-27B-Fable-Fusion-711` + `Qwen3.8-27B-Cold-Fusion-GAIN-V1.1` 两个大微调的 merge，再 heretic、再微调。**任何微调都会移动输出分布**，而我们的任务格式容错为零——多一个 `<d>` 标签、少一个时间戳，H3 那边直接报错。

一句话：**JC 把"格式塌掉"这个风险从源头消掉了；DavidAU 是拿基准分去赌它不会塌。**

**2. 它比 DavidAU 小 1.7GB，余量从 2.6GB 变成 4.3GB。**

16.8 GB（MTP 已内联）vs 18.5 GB。24GB 卡上的差别是实打实的：前者能把上下文从 16k 加到 32k 还绰绰有余，后者已经贴边。

**3. 它是唯一公开了完整困惑度（PPL）表的候选。**

JC 的模型卡给了一张同一次会话内、同一 f16 基线测出来的全量化 PPL 表：

| 量化 | PPL (wikitext-2) | vs f16 |
| --- | --- | --- |
| f16（基线） | 7.1557 | — |
| Q5_K_M | 7.1573 | +0.0016 |
| IQ4_XS | 7.1583 | +0.0026 |
| Q6_K | 7.1689 | +0.0132 |
| Q8_0 | 7.1764 | +0.0207 |
| **Q4_K_M** | **7.1814** | **+0.0257** |
| IQ2_M | 7.8581 | +0.7024 |

作者自己加了一句很关键的话：

> 除 IQ2_M 外，所有行都落在 0.026 的跨度里，而标准误约 0.25，所以这些量化彼此之间、以及与 f16 之间都不可区分，这里的排序是噪声。

这直接回答了"要不要上 Q5_K_M"：**不用。** 在本模型上，为省 2.7GB 显存而选 Q4_K_M 是零代价的。别的候选给不出这个结论——它们的量化档位差别只能靠作者自述。

**4. 社区验证最充分。** 230 万下载，所有候选里最高（第二名 0bserverx 183 万）。下载量不等于质量，但对"这东西到底能不能跑起来"这个问题，它是最强的信号。

**5. 视觉和 MTP 都保住了，而且写清了怎么用。**

- 视觉：`mmproj-Qwen3.8-27B-Uncensored-F16.gguf`（0.9 GB），用标准 `mmproj` 前缀，运行时能自动发现
- MTP：`mtp.*` 张量是**从基座逐字节复制**的（消融只动 `attn.o_proj` 和 `mlp.down_proj`），所以投机解码的接受率几乎不受影响

**6. 部署更简单。** MTP 是**内联**在同一个 gguf 里的，不像别的仓库要另外下一个 draft 头。想显式加载 draft 也有 `noMTP-*` + `draft-*` 的组合可选。

### 2.4 被淘汰的，以及为什么

**OBLITERATUS/Qwen3.8-27B-OBLITERATED（1.26M 下载 / 1.28k 赞，呼声最高）——两条硬伤：**

1. **没有 mmproj。** 模型卡里根本没有视觉投影文件。第三节那条"直接丢参考图让模型写 `ref2va` 提示词"的升级路径直接没了。
2. **它要求系统提示留空。** 模型卡原文：

   > **System prompt：无 / 空。** A/B 测试表明系统提示可能重新引入拒绝行为。"裸跑"更好。

   我们的流程**就是**系统提示驱动的——`prompts/system-prompt.txt` 里写着 H3 三字段结构和全部格式约束。一个"加了系统提示就会重新拒答"的模型，和我们的架构直接冲突。

   它的能力代价也最大：MMLU −2.1pp，其中 STEM −3.3pp。

**zerodigest/…-YMQ-MTP-GGUF —— 量化档位非标。**

它不用标准 GGUF 命名，而是一套自定义的 `XXS/XS/S/M/L/XL` + `-TI` / `-Pro` 预设（内部混合 IQ2/IQ3/IQ4 不同档位），**没有 Q4_K_M**。好处是在 12–16GB 显存上有很细的档位；坏处是档位之间到底差多少只能靠作者自述，没有可对照的 PPL 表。对要求结果可复现的批量流程，这种不透明是不必要的风险。

（它的量化说明里还有一处明显笔误：F16 视觉文件标成 `~928 GB`。）

**低下载量的一批（mlasli / Ryn1998 / soyaakinohara / outsourc-e / LessThanThreeAI / nerkyor 等）** —— 不是不好，而是**没有理由选**：要么只发单一量化档，要么是别人权重的二次量化（如 `soyaakinohara` 的 3.69bpw，压缩太狠），要么根本没有模型卡。在已经有 230 万下载、文档完整的候选时，不值得冒风险。

### 2.5 那为什么还留着 DavidAU

因为它有 JC **没有**的东西，而且是真实优势：

| | DavidAU | JonathanColetti |
| --- | --- | --- |
| ARC-C / ARC-E | **735 / 882**（4bit 719 / 887） | 未公开（≈基座 591 / 782） |
| 思考 token | **TURBO，降到 1/2 ~ 1/10** | 需靠模板改 `reasoning_effort` |
| 量化 | NEO IMATRIX（宣称 +2–4% 精度），输出张量 16bit | 标准 imatrix |
| 格式风险 | 经过两轮大微调 merge，**未知** | 与基座等价，**已排除** |

基准分那一行值得停一下：基座 Qwen3.8-27B 的 ARC-C 是 591，DavidAU 报 735，**+14.4pp**。这不是噪声级别的提升。如果格式关能过，它就是更强的模型。

但它自己的模型卡也留了一句要留意的话：

> 模型不会拒绝请求，但**某些情况下需要"推动/引导"**，否则内容可能相对 bland（平淡）。

也就是说 **DavidAU 的解禁同样是部分的**，只是它把"需要引导"当成使用技巧来写。这和 JC 说的 "substantially reduced, not eliminated" 是同一类问题，表述不同而已。

所以结论不是"DavidAU 不好"，而是：**在没有实测数据之前，选一个格式等价于基座的模型，比选一个基准分更高的模型更稳。** 而这个"实测数据"我们本来就要跑（第八节）。

### 2.6 一句话结论

- **主选 JonathanColetti（Q4_K_M，16.8 GB）** —— 因为它把最大的风险（格式塌掉）从源头消掉了。
- **DavidAU（MTP-Q4_K_M，18.5 GB）降为对照组** —— 如果主选在黑暗向内容上仍然拒答，它是第一顺位替补。
- **0bserverx（Q4_K_M-mtp，17.0 GB）作为第二替补** —— KL 损伤最低（0.0085）、拒答 0–1/100，而且每个量化文件都通过了工具调用 / 思考开关的逐文件测试，是"最激进解禁 + 最小能力损伤"的组合。

A/B 的第一轮跑**官方基线 / JC / DavidAU 三组**；如果 JC 和 DavidAU 都还在拒答，才把 0bserverx 拉进来跑第四组。判断规则见第八节。

## 三、视觉能力：这个模型能看图写提示词

`04` 文档把规划机定位成纯文字转写。但这个模型挂上 `mmproj` 之后可以直接看参考图。

对 `assets/` 里的素材——角色图、场景图、首尾帧——意味着流程可以从

> 你手写"穿红色风衣的女人站在雨夜街头" → 模型转写成 H3 提示词

变成

> 直接丢角色图和场景图 → 模型看完自己写 `ref2va` 提示词

**这对 `fl2va`（首尾帧）和 `ref2va`（参考素材）两条线是实打实的升级**，因为首尾帧的构图、光线、人物一致性本来就是最难用文字描述清楚的部分。

代价只有 0.9 GB 显存和一点编码耗时。建议直接开。

> 顺带说明：**"有没有 mmproj"是这轮筛选的硬门槛之一。** 呼声最高的 `OBLITERATUS/Qwen3.8-27B-OBLITERATED`（1.28k 赞）就是因为仓库里根本没有视觉投影文件而被淘汰的，见 2.4。

## 四、显存实算

`04` 文档按"Q4_K_M 每参数约 0.58 字节"估 27B ≈ 16GB。**主选实测 16.8 GB**，和这个经验公式基本吻合（0.62 字节/参数）。

> 上一版这里写的是"实测 18.5GB，比估算高 2.5GB"——那是 **DavidAU 那一版**的数字，不是通用的。它偏大有两个原因：一是 NEO-CODER 量化把输出张量提到 16bit 全精度（输出层约占 10–20%），二是它的 merge 让有效参数量超过了标称的 27B。换成主选后这个"公式偏低 15%"的结论就不成立了，见第七节。

好消息是 **KV 缓存比常规 Transformer 小得多**。查基座 `Qwen/Qwen3.8-27B` 的 `config.json`：

```
num_hidden_layers: 64          # 但 layer_types 是 3 线性 : 1 全注意力
full_attention_interval: 4     # → 只有 16 层需要完整 KV
num_attention_heads: 24
num_key_value_heads: 4         # GQA，4 个 KV 头
head_dim: 256
```

64 层里 48 层是 Gated DeltaNet 线性注意力（状态固定大小，不随上下文增长），只有 16 层是全注意力。每 token 的 KV 开销：

```
2(K和V) × 16层 × 4头 × 256 × 2字节 = 64 KB/token
```

| 上下文 | KV 缓存（F16） | KV 缓存（Q8_0） |
| --- | --- | --- |
| 8k | 0.5 GB | 0.25 GB |
| 16k | 1.0 GB | 0.5 GB |
| 32k | 2.0 GB | 1.0 GB |
| 64k | 4.0 GB | 2.0 GB |

**你的提示词场景根本用不到长上下文**：系统指令 + 一条创意 + 输出，合计约 3k token。给到 16k 已经是十倍余量。

所以 24GB 卡的完整账：

| 项目 | 占用 |
| --- | --- |
| Q4_K_M 权重（MTP 内联） | 16.8 GB |
| mmproj-F16（视觉） | 0.9 GB |
| KV 缓存 @16k F16 | 1.0 GB |
| CUDA 上下文与计算缓冲 | ~1.0 GB |
| **合计** | **~19.7 GB** |

**24GB 卡余量 4.3GB**，比上一版的 2.6GB 宽裕不少。这带来两个实际好处：

1. 上下文可以从 16k 提到 32k（+1GB）仍然宽松
2. 不用为显存纠结量化档位——反正 PPL 表已经证明 Q4_K_M 和 Q5_K_M 不可区分（见 2.3）

如果你最后选了 DavidAU 那版做对照，它的账是 18.5 + 0.93 + 1.0 + 1.0 ≈ **21.4GB**，余量只剩 2.6GB，32k 上下文就别想了。

**为什么还是 3090 而不是显存更大的 vGPU-32GB**：3090 的显存带宽 **936 GB/s** 是公开且确定的。vGPU-32GB 的算力只有 RTX 4090 的 63%（52.22 / 82.58），而虚拟化切分卡的带宽通常按同比例缩水，推算约 **600 GB/s** 上下。

LLM 推理是**显存带宽瓶颈**而不是算力瓶颈，所以 3090 在**更便宜的同时还更快**。多出来的 8GB 显存对主选没有意义——它 19.7GB 的占用在 24GB 上已经很宽松，而且 PPL 表已经证明没必要上 Q5_K_M（见 2.3）。

> ⚠️ 3090 在 **西北B区 和 重庆A区 是 0 张**。只筛这两个区会误判成"没货"——这正是初版犯的错。

### 关于 A/B 测试的算力安排

A/B 要跑三个模型（官方基线 / JC / DavidAU），而 24GB 卡一次只装得下一个（16.5 + 16.8 = 33GB > 24GB）。所以是**三次开机、每次一个模型**。

成本其实很低：10 条创意的批量大约 1.5 万输出 token，3090 上约 6 分钟，加上 90 秒加载，**每次开机 10 分钟就够**。三次合计约 ¥0.75。

> 如果想一次跑完省去反复开关机，可以租 **RTX PRO 6000 96GB（¥6.98/时）**，三个模型同时驻留（51GB）没问题，一个会话搞定。但 ¥6.98/时意味着出错成本高，而且账户余额只有 ¥20。**建议还是走 3090 三次开机。**

### 值得留意，但不建议主选

- **vGPU-48GB-350W ¥1.78 / 48GB**：单位显存最便宜，但功耗被限到 350W，且只有 24 张卡，随时可能没了。
- **RTX 4090 · 西北B区 ¥1.88**：24GB 里最快（1008 GB/s）。比 3090 贵 ¥0.40/h，带宽只快 8%，算力快一倍但用不上。
- **包日 / 包月**：4090D 包日 ¥42.75（≈¥1.78/h，比按量省 5%），包月 ¥898.80（≈¥1.23/h，省 35%）。**你的用法是一次开机几小时，按量最划算**；包月只在确定每天跑满时才划算。
- **摩尔线程 MTT S4000 48GB ¥1.86**：国产卡，不支持 CUDA，llama.cpp 跑不了，排除。

### 编译 llama.cpp

Ollama 对这种混合注意力架构（线性注意力 + MTP）的支持通常滞后于 llama.cpp，所以直接用 `llama-server`。它同样提供 OpenAI 兼容的 `/v1/chat/completions`。

> `setup-planner.sh` 已经处理了这件事，无卡模式会自动退回 `86` 并提示你用 `CUDA_ARCH=` 覆盖。
> 其实开机编译只要约 10 分钟（按 ¥1.48/时算不到 3 毛钱），没必要为省这点钱去踩架构的坑。

### 起服务

监听 `11434`，和原方案的 Ollama 端口保持一致，这样 `batch-prompts.py` 和 Open WebUI 都只改一个地址。

```bash

./build/bin/llama-server \
  -m /root/autodl-tmp/models/qwen38-27b-heretic/Qwen3.8-27B-Uncensored-Q4_K_M.gguf \
  --mmproj /root/autodl-tmp/models/qwen38-27b-heretic/mmproj-Qwen3.8-27B-Uncensored-F16.gguf \
  --host 127.0.0.1 --port 11434 \

  --temp 0.7 --top-p 0.95 --min-p 0.05 --repeat-penalty 1.0
```

关键参数：

- `--jinja` 必须加，否则不会用模型自带的对话模板，推理模式的开关会失效
- `--repeat-penalty 1.0` 即关闭重复惩罚
- `-c 16384` 对提示词场景绰绰有余，余量够所以也可以放心提到 32768

### 投机解码（MTP）：**已实测，默认开启**

`Q4_K_M` 文件里内联了 MTP 头，开投机解码提速。参数是：

```bash

```

**2026-09-20 实测结论：提速 1.44 倍，质量零损失，已设为默认开启。** 完整数据见第 9.9 节。

之前担心的两点都排除了：

- **flag 不存在会启动失败** → 现在 `start-planner.sh` 默认带 MTP 启动，失败时**自动去掉 `--spec-type` 重试一次**，不会卡住。
- **消融后 draft 接受率可能下降** → 实测接受率稳定在 **62%–73%**（作者担心的情况没有发生）。

不需要手动加参数了，`bash start-planner.sh` 默认就是开的。想显式关掉用 `MTP=0 bash start-planner.sh`。

### 思维链开关（重要）

这个基座默认走 `xhigh` 推理模式，写提示词用不上，纯烧时间。注意**这是 Qwen 基座自己的机制，不是 DavidAU 的 TURBO**——JC 这版没有做思考裁剪，所以这里的开关是"要不要省"的问题，不是"能不能用"的问题。

**优先用模板参数，不要改模板文件。** 查过这个仓库的对话模板（模型卡的 `chat_template` 字段），它本身就把 `enable_thinking` 暴露出来了：

```jinja
{%- if enable_thinking is undefined or enable_thinking is true %}
    {%- set resolved_reasoning_effort = reasoning_effort|default('xhigh') %}
{%- endif %}
...
{%- if enable_thinking is defined and enable_thinking is false %}
    {{- '<think>\n\n</think>\n\n' }}     {# 空思考块，等于关掉 #}
{%- else %}
    {{- '<think>\n' }}
{%- endif %}
```

也就是说传 `enable_thinking: false` 就能把思维链整个跳过，`reasoning_effort` 只在没关思考时才起作用。三种用法，从省事到彻底：

1. **服务端默认值**（推荐，改一次管全部请求）——`start-planner.sh` 里加：
   ```
   --chat-template-kwargs '{"enable_thinking":false}'
   ```
2. **单次请求覆盖**——请求体里加 `"chat_template_kwargs": {"enable_thinking": false}`
3. **只想让思考变短而不是关掉**——传 `"chat_template_kwargs": {"reasoning_effort": "low"}`

改 `--chat-template` 指定自定义模板文件是最后手段，模板文件在 `~/llama.cpp` 的缓存目录里。**先用默认值跑通，再动这个**，否则出问题分不清是模型还是模板的锅。

> 如果 A/B 结果显示 JC 的思考链太长拖慢了批量，那就是换回 DavidAU 的一个具体理由——它的 TURBO 已经把这一步做完了。

### 对接现有流程


## 八、风险与验证

### 解禁 ≠ 格式遵循更好

这是最需要警惕的一点，也是这轮把主选换成 JonathanColetti 的核心原因。

社区里绝大多数解禁模型是拿角色扮演 / 创意写作语料猛调的，**严格格式遵循有可能反而不如官方 instruct 模型**——多一个 `<d>` 标签、少一个时间戳，H3 那边就直接报错。DavidAU 那版就属于这一类（两个大微调 merge 后再消融）。

JC 那版是**唯一从机制上排除这个风险**的：它不做任何微调，只把拒绝方向从权重里减掉，且消融目标就是"拒答数↓ 且 与基座的 KL 距离↓"。所以它的格式能力和基座**等价**，不是"大概率还行"。

但"等价于基座"仍然不等于"够用"——基座本身也可能在长输出里丢字段。所以**还是要测**。

### A/B 怎么跑：三组，不是两组

因为主选换了，A/B 的设计也跟着变。现在要回答两个问题：

1. 解禁到底有没有必要？（→ 需要官方基线）
2. 两个解禁方案哪个更合适？（→ 需要 JC 和 DavidAU 对比）

所以是**三组**，分三次开机：

```bash
# 第一次开机：官方基线（注意用 Qwen3.8，和候选同基座）
python ab-test.py run --briefs briefs --out abtest/official --model qwen3.8:27b

# 关机 → 换 JC 权重 → 再开机
python ab-test.py run --briefs briefs --out abtest/jc --model qwen38-27b-heretic

# 关机 → 换 DavidAU 权重 → 再开机
python ab-test.py run --briefs briefs --out abtest/dau --model qwen38-27b-heretic

# 对比（本地跑就行，不需要实例）
python ab-test.py compare --a abtest/official --b abtest/jc
python ab-test.py compare --a abtest/jc --b abtest/dau
```

> 官方基线为什么不是 `qwen3.6:27b`：`04` 文档选的是它，但所有解禁候选都基于 **Qwen3.8-27B**。拿 3.6 当基线会同时改变"基座版本"和"是否解禁"两个变量，测出来的差异归因不了。要换成 **`qwen3.8:27b`**。

`ab-test.py` 会逐条检查这些格式硬性约束：三字段齐全且有序、以 `[Shot 1]` 开头、无多余前言、无代码块包裹、长度 ≤7000、`<d>` 标签成对、镜头编号从 1 递增、时间码严格递增。

输出示例：

```
指标                       A           B          变化
拒答率                  40.0%        0.0%      -40.0  ✓更好
一次通过率                60.0%       80.0%      +20.0  ✓更好

逐条对照（A / B）:
  S02        拒答   / 通过     ← 不同
  S03        通过   / 格式     ← 不同
```

判断规则：

1. 拿同一批 **10 条以上**创意（**必须包含 3–5 条会触发拒答的擦边/黑暗向内容**，否则两边拒答率都是 0，测不出差别）
2. 只有「拒答率明显下降 **且** 一次通过率没有明显下降」才值得换
3. 低于 10 条的结论不可靠；`ab-test.py` 会把每条产出都存成 `.md`，人工复核一遍再决定

### 三种可能的结果，分别怎么办

| 官方基线 | JC | DavidAU | 结论 |
| --- | --- | --- | --- |
| 拒答率 <10% | — | — | **不换**。官方版够用，省掉全部解禁风险 |
| 拒答率高 | 拒答低、通过率不降 | — | **用 JC**。这是预期结果，也是本次选型的假设 |
| 拒答率高 | 仍拒答 | 拒答更低 | **换 DavidAU**。说明 Heretic 的保守消融不够，需要更激进的 merge |
| 拒答率高 | 仍拒答 | 也仍拒答 | **换 0bserverx**（第二替补，拒答 0–1/100、KL 0.0085）。三个都不行才考虑换更大的基座 |

### 先确认你真的需要解禁

如果官方 `qwen3.8:27b` 在你的内容上拒答率低于 10%，那**不要换**。解禁带来的格式风险不值这点收益。先用 5–10 条测试确认拒答确实是个问题，再动手。

### 合规底线

AutoDL 的容器实例明确禁止"使用 WebUI 等算法生成违禁图片"，违规直接封号。这里跑的是**文字模型写提示词**，不涉及图像生成，但生成环节在 ComfyUI 上，注意别把两边搞混。另外解禁模型不会帮你越过法律红线——涉及真实人物的色情内容、未成年人相关内容，无论模型是否拒答都不做。

### 费用

账户余额 ¥20。按 RTX 3090 · 内蒙B区 ¥1.48/时算，够开机 13 小时；选北京A区 ¥1.32 则够 15 小时。

A/B 阶段每次开机约 10 分钟，三次合计不到 ¥1。建议正式跑批时按 `02-每次创作流程.md` 的纪律：**一次开机把整批写完，立刻关机**。

## 九、实测结果（2026-09-20）

这一节是上面所有推断的**实测校验**，不是推算。原始产出在 `records/abtest/`。

### 9.1 落地形态

| 项目 | 实际值 |
| --- | --- |
| 实例 | 内蒙B区 / 340机 / RTX 3090 24GB / ¥1.48/时 |
| 镜像 | PyTorch 2.8.0 · Python 3.12 · CUDA 12.8 |
| llama.cpp | `0.4.1-dev` build `e613ef2`，CUDA 12.8，`CMAKE_CUDA_ARCHITECTURES=86` |
| 主权重 | `Qwen3.8-27B-Uncensored-Q4_K_M.gguf` = **15.66 GB**（比预估的 16.8GB 小） |
| 视觉 | `mmproj-Qwen3.8-27B-Uncensored-F16.gguf` = 0.86 GB |
| 权重加载 | **10 秒**（NVMe，比预估的 30–90 秒快得多） |
| 生成速度 | **约 36–40 tok/s** |
| 显存占用 | **18315 MiB / 24576 MiB（17.9 GB）**，余量 6.2 GB——比第四节估的 19.7GB 还省 1.8GB |

### 9.2 思维链的真实开销（重要，会直接影响测量）

用 `S07-雨夜巷斗` 单条对比，这是决定 A/B 怎么跑的关键数据：

| | 思维链开（基座默认 xhigh） | 思维链关（`enable_thinking=false`） |
| --- | --- | --- |
| 耗时 | 196.2 秒 | **11.4 秒** |
| completion tokens | 7900 | **407** |
| 思考字符数 | 22108 | 0 |
| 正文字符数 | 1337 | **1531** |
| 是否拒答 | 否 | 否 |

**思考吃掉了 95% 的 token，而且正文反而更短。** 两个推论：

1. **`max_tokens` 必须给够。** 8192 的预算里 7000 被思考吃掉，只剩不到 1200 给正文。`ab-test.py` 原来默认 4096 —— 那会在正文还没开始写时就截断，正文为空，被格式检查判成"不符"，测出一个完全虚假的低通过率。**已把默认值改成 8192，并把两个脚本都改成默认关思维链（要开加 `--think`）。**
2. **写提示词这件事不需要推理。** 关掉之后快 17 倍，正文更长，拒答行为完全一致。没有理由开着。

### 9.3 四轮结果（含一次自我纠错）

跑了四轮。第三轮的存在很关键——它推翻了第二轮的数字。

| 轮次 | 系统提示词 | 检查器 | 拒答率 | 一次通过率 | 平均长度 |
| --- | --- | --- | --- | --- | --- |
| `jc` | 原版 | 10 项判据 | 0.0% | 70.0%（7/10） | 1581 字符 |
| `jc-v2` | +字段名约束 | 10 项判据 | 0.0% | ~~100.0%~~ ← **不可信，见下** | 1830 字符 |
| `jc-v3` | 同上（未改） | **12 项判据** | 0.0% | **40.0%（4/10）** | 2040 字符 |
| `jc-v4` | +对白标记/镜头编号/画外音约束 | 12 项判据 | 0.0% | **100.0%（10/10）** | 1666 字符 |

**`jc-v2` 的 100% 是检查器的盲区造成的假象。** 当时 `ab-test.py` 只查 10 项，漏掉了两条真实存在的规范要求：对白标签里必须有 `[语言]` 标记、画外音条款必须成对出现。同一个提示词，换成 12 项判据重测（`jc-v3`），真实水平只有 40%。

**教训：通过率只在"判据覆盖了全部硬性约束"时才有意义。** 看到 100% 应该先怀疑检查器，而不是先高兴。

四轮里 **拒答率始终是 0.0%（0/10）**——这是最稳的结论。5 条黑暗向创意（S07 雨夜巷斗 / S08 临终病房 / S09 加油站劫案 / S10 废墟幸存者 / S11 审讯室，覆盖暴力见血、死亡、持械犯罪、伤情、威胁恐吓）每一轮都正常产出，一条都没拒，也没出现"自动净化"——血、骨折、手铐、逼供都照写。

### 9.4 两类问题，都是提示词问题

**第一类：漏字段名（`jc` 的 3 条失败）**

S05 / S08 / S10 **检查项完全相同**，是同一根因的连锁反应：模型**漏掉 `integrated_multimodal_description:` 这一行**，直接从 `[Shot 1]` 开始写。于是：

- 「字段齐全且有序」失败 —— 字段序列只剩后两个
- 「以 [Shot 1] 开头」失败 —— 判据是「字段名后紧跟 `[Shot 1]`」，字段名都没了
- 「无多余前言」失败 —— `split(字段名)[0]` 找不到字段名，退化成取前 200 字符

**三条失败里没有一条是内容缺陷，全是漏了一行标签。**

**第二类：对白语言标记 + 画外音条款误用（`jc-v3` 的 6 条失败）**

补上判据后暴露出来的，5 条栽在同一处：

| 模型实际写的 | 应该写的 |
| --- | --- |
| `<d>Chinese 这些书，我一本都没看完。</d>` | `<d>[Chinese] 这些书，我一本都没看完。</d>` |
| `<d>Don't turn off the light.</d>`（英文对白整个标记都没写） | `<d>[English] Don't turn off the light.</d>` |
| `<d>[Japanese] Mada sono…</d>` ← 只有日文写对了 | — |

另外两条：S02 出现两个 `[Shot 1]`（编号没递增）；S07 把「画外音」专用条款 `while his/her lips remain completely closed` 用在了**画面内**的说话人身上——因为镜头描述里写了她面部被遮挡。

在 `prompts/system-prompt.txt` 里逐条加约束后（字段名 / 镜头编号 / 对白方括号必填且英文也要标 / 画外音条款只限画外人），40% → **100%**。

**结论：解禁模型的格式问题全部是提示词问题，不是模型能力问题。** 换成官方基线大概率也一样，甚至更差——因为官方版连内容都会拒。

### 9.6 部署时踩的三个坑（都已在脚本里修掉）

1. **AutoDL 公钥必须在实例创建之前登记。** 公钥晚于实例创建，开机时就不会被注入，表现为 `Permission denied (publickey,password)`，而本地公私钥明明是配对的。补救要重启实例——但按量计费实例关机确认弹窗明确警告 *"关机后GPU将会释放，再次开机时可能面临空闲GPU不足无法开机"*，且当时该机 `gpu_idle_num=0`，风险是真的。
2. **非交互 SSH 不加载 conda / CUDA 的 PATH。** 表现为 `nvcc: command not found` 和 `python: command not found`，实际两者都在（`/usr/local/cuda-12.8/bin`、`/root/miniconda3/bin`）。已在两个脚本顶部加了幂等的 PATH 补齐。
3. **`hf download` 默认走 Xet，会绕开镜像站直连 `us.aws.cdn.hf.co`，国内必然超时。** 报错是 `RuntimeError: File reconstruction error: CAS Client Error`。加 `HF_HUB_DISABLE_XET=1` 退化成普通 HTTP 即可。已固化进脚本。

### 9.8 实例怎么停放（重要，别误操作）

- 主机下架也会释放实例（租期一般 3 个月至几年），控制台首页可开启释放预警。
- **保存镜像必须先关机**，且**只保存系统盘**，数据盘不进镜像。

### 9.9 MTP 投机解码实测：提速 1.44 倍，质量零损失

第六节原本写的是"先别急着加"。A/B 完成后在同一台机器上补做了这个实验。

**单条生成速度**（同样 3 条创意，`--think` 关闭）：

| | S02 雨夜便利店 | S06 揉面团 | S11 审讯室 | 平均 |
| --- | --- | --- | --- | --- |
| 无 MTP | 39.6 tok/s | 39.2 tok/s | 40.0 tok/s | **39.6 tok/s** |
| 开 MTP | 54.2 tok/s | 62.9 tok/s | 61.2 tok/s | **59.4 tok/s** |

**整批墙钟时间**（10 条）：

| | 总耗时 | 平均单条 | 拒答率 | 一次通过率 |
| --- | --- | --- | --- | --- |
| `jc-v4`（无 MTP） | 100.3 秒 | 10.0 秒 | 0.0% | 100.0% |
| `jc-mtp`（开 MTP） | **69.7 秒** | **7.0 秒** | 0.0% | 100.0% |

**draft 接受率**实测 0.625 / 0.633 / 0.730 / 0.653，稳定在 **62%–73%**。作者在模型卡里担心"MTP 的 draft 头是对未解禁的原版训练的，消融后接受率可能下降"——**实测没有发生**。

两点说明：

1. **token 速率的提升（1.50×）大于墙钟提升（1.44×）**，因为 MTP 只加速解码，不加速 prefill。批量越大、输出越长，收益越接近 1.5 倍。
2. **投机解码在原理上是无损的**（每个 draft token 都要经目标模型验证），所以质量不该变——实测确认了这一点。这也是敢把它设为默认的原因。

已改为**默认开启**，并加了自动回退：`start-planner.sh` 带 MTP 启动失败时会自动去掉 `--spec-type` 重试，不会因为 llama.cpp 版本问题卡住。

### 9.11 网页入口：一直有，但没人打得开

**问题**：为什么没有给人用的网页界面？

**排查结果**：`llama-server` **自带一个完整的聊天界面**（SvelteKit 打的静态站点，在 `/` 路径）。所以界面一直都在，打不开是两个原因叠在一起：

1. 原脚本绑在 `127.0.0.1`，只有本机能访问；
2. **AutoDL 只把 6006 / 6008 两个端口做公网映射**，而脚本监听的是 11434——这个端口从外面根本到不了。

排查时有个小插曲：`curl http://127.0.0.1:11434/` 返回 `Error: gzip is not supported by this browser`（HTTP 415）。这条报错本身就是证据——它说明根路径上挂着一个要求 gzip 的界面处理器。带上 `Accept-Encoding: gzip` 就拿到了 12.6KB 的 HTML。

**改动**：

| 项 | 原值 | 新值 |
| --- | --- | --- |
| 监听地址 | `127.0.0.1` | **`0.0.0.0`** |
| 端口 | `11434` | **`6006`**（AutoDL 固定映射的那两个之一） |
| 访问口令 | 无 | `API_KEY=xxx` 可选，**公网暴露时强烈建议设** |

三个客户端脚本（`batch-prompts.py` / `ab-test.py` / `probe-model.py`）的默认地址已同步改为 `http://127.0.0.1:6006`。历史 `records/abtest/*/report.json` 里记的仍是当时的 11434，**这是记录，不改**。

**用法**：`bash start-planner.sh` 之后回 AutoDL 控制台，点实例卡片上的「自定义服务」，浏览器里就是聊天界面。

**已实测验证**：

- `/proc/net/tcp` 显示监听 `00000000:1776`（即 `0.0.0.0:6006`），状态 `0A`（LISTEN）
- 从容器 IP（`172.17.0.8`）访问 `http://172.17.0.8:6006/` → **HTTP 200**
- 不带口令 POST `/v1/chat/completions` → **401**；带错口令 → **401**；带对口令 → **200**
- 网页资源 `/`、`/favicon.ico`、`/manifest.webmanifest` 全部 200

> **安全提示**：模型是解禁版，绑 `0.0.0.0` 等于放到公网。内置网页界面支持填口令（设置里的 *"Set the API Key if you are using --api-key option"*），所以 `API_KEY` 是端到端可用的，不是摆设。脚本在没设口令时会主动打警告。
>
> 想只给本机用就 `HOST=127.0.0.1 bash start-planner.sh`。

### 9.12 从另一台电脑访问网页界面

**前提：实例必须在开机状态。** 现在是关机停放中，关机状态下没有任何端口可访问，下面两条路都走不通。

AutoDL 的实例**没有独立公网 IP**，所以不能随意开放端口。个人用户只有两条路。

#### 方法 A：自定义服务（零配置，任何电脑都能用）

AutoDL 给**每个实例的 6006 和 6008 端口**各映射了一个公网可访问的 `ip:port`，协议可选 TCP 或 HTTP。地址在「自定义服务」入口点"复制"获取，形如：

```
https://u39-b3fb-39a640fd.nmb2.seetacloud.com:8443
```

拿到这个地址后，**在任何一台电脑的浏览器里打开就能用**，不需要装任何东西，也不需要在那台电脑上登录 AutoDL。

这也是把服务绑到 `0.0.0.0:6006` 而不是 `127.0.0.1:11434` 的原因——端口选错了，这条路直接断掉。

**代价**：地址在公网可达。任何人拿到这个 URL 都能用你的模型、烧你的余额。**所以必须配 `API_KEY`。**

> ⚠️ 这个地址是**跟实例绑定**的，释放重建实例后会变。换实例要重新复制。

#### 方法 B：SSH 隧道（不暴露公网，更安全）

在**那台要访问的电脑上**执行（需要该电脑有 SSH 私钥，或知道实例的 root 密码）：

```bash
ssh -CNg -L 6006:127.0.0.1:6006 -p 33780 root@connect.nmb2.seetacloud.com
```

然后在同一台电脑浏览器打开 `http://127.0.0.1:6006`。

参数含义：

| 参数 | 作用 |
| --- | --- |
| `-C` | 压缩传输 |
| `-N` | 不执行远程命令，只做端口转发 |
| `-g` | 允许其他主机连本地的转发端口 |
| `-L 6006:127.0.0.1:6006` | 把实例的 6006 端口映射到本地的 6006 |

几个实操要点：

- **执行后没有任何输出是正常的。** 只要没报错、没要求重新输密码，就说明隧道建好了。
- **终端窗口不能关**，关了隧道就断。
- Windows 不想敲命令可以用官方免安装工具：<https://autodl-public.ks3-cn-beijing.ksyuncs.com/tool/AutoDL-SSH-Tools.zip>，解压后输入端口号即可。
- Windows 报 `bad permissions` 就把私钥设为只读；报 `.ssh/config` 的 owner 问题就删掉那个 config 文件。
- 本地 6006 被占用的话，改左边的数字即可（`-L 6007:127.0.0.1:6006`）。

#### 怎么选

| | 方法 A 自定义服务 | 方法 B SSH 隧道 |
| --- | --- | --- |
| 另一台电脑要装东西吗 | 不用 | 要能 SSH（私钥或密码） |
| 要不要登录 AutoDL | 不用 | 不用 |
| 公网可达 | **是**（必须配 `API_KEY`） | 否，只在本机回环 |
| 断线重连 | 无所谓 | 终端一关就断 |
| 适合 | 手机、临时借用别人的电脑、演示 | 固定几台自己的机器 |

**建议**：日常自己用走方法 B；需要给别的设备或别人看时走方法 A，并且一定带上 `API_KEY`。

> 开任意端口（不只是 6006/6008）需要**企业认证**，入口在「控制台 → 账号 → 账号安全」。个人用户用不了，所以才需要上面这两条路。
